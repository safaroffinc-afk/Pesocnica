# ТЕХНИЧЕСКОЕ ЗАДАНИЕ №4

## Quotes, Site Visits & Deal Flow

**Проект:** «Стройка и Ремонт — Филадельфия и Пенсильвания» / Construction Marketplace Pennsylvania
**Версия:** 1.0
**Назначение:** постановка задачи разработчикам backend, CRM, customer dashboard и contractor app
**Связанные модули:** ТЗ №1 — Contractor Acquisition, ТЗ №2 — Customer Acquisition & Project Intake, ТЗ №3 — Matching Engine
**Основная цель:** превратить interested-подрядчиков в сравнимые сметы, помочь клиенту выбрать мастера и зафиксировать сделку внутри платформы — с суммой, датами и документами.

> Живая версия документа (комментарии, правки): https://claude.ai/artifact/VBuWAprToJTzsx9fPqQEaU

## 1. Главная бизнес-задача

Модуль закрывает отрезок воронки между Matching Engine (ТЗ №3) и выполнением проекта:

```text
Contractor INTERESTED
        ↓
   Site Visit (опционально)
        ↓
   Quote (preliminary → final)
        ↓
   Comparison + переговоры в чате
        ↓
   SELECT CONTRACTOR
        ↓
   DEAL: сумма + даты + документы
        ↓
   Change Orders → Final Value
```

Модуль должен:

1. дать подрядчику быстрый и структурированный способ подать смету;
2. сделать сметы **сравнимыми** между собой (одинаковые поля, нормализация);
3. организовать осмотры объекта (site visits) с календарём и напоминаниями;
4. вести переговоры в чате платформы с маскированием контактов до выбора;
5. зафиксировать выбор подрядчика как Deal — юридически и аналитически значимую запись;
6. раскрыть контакты и адрес только после фиксации сделки;
7. вести Change Orders и считать Final Value — основу метрики Total Project Value Created;
8. корректно обрабатывать срыв сделки (возврат в matching) и споры;
9. отдать аналитике полные данные: quote rate, время до сметы, конверсию quote → hire, цены против бюджетов.

Деньги через платформу (escrow, payment processing) в этот модуль **не входят** (ТЗ №2 §101) — фиксируются только суммы и факты.

## 2. Место в системе

Модуль работает над теми же сущностями, что и ТЗ №2–№3: Project, ContractorInvitation, Conversation. Он потребляет событие `invitation.responded (interested)` из Matching Engine и возвращает системе события `quote.*`, `visit.*`, `deal.*`. Статусы проекта на этом отрезке (ТЗ №2 §41): `contractors-interested → quotes-received → customer-comparing → site-visit → contractor-selected → scheduled`.

## 3. Ключевые принципы

* **Сравнимость важнее гибкости.** Смета — структурированный объект с обязательными полями, а не свободный текст или PDF. PDF можно приложить, но он не заменяет поля.
* **Платформа не выбирает за клиента.** Бейджи («лучшая цена», «самый ранний старт») — факты, а не рекомендации; сортировка по умолчанию нейтральна (по дате получения).
* **Сделка фиксируется внутри платформы.** Без Deal-записи нет verified review, нет Trust Score, нет защиты при споре — это экономический стимул против обхода.
* **Каждое изменение цены — версия или Change Order.** История цены неизменяема и видна обеим сторонам.
* **Скорость.** Подача базовой сметы с телефона — до 2 минут; сравнение для клиента — один экран без прокрутки таблиц на mobile.

## 4. Глоссарий

| Термин | Значение |
| --- | --- |
| Quote | смета подрядчика по конкретному проекту |
| Preliminary quote | ориентировочная вилка до осмотра объекта |
| Final quote | смета после осмотра / уточнения scope |
| Quote version | неизменяемый снапшот сметы на момент отправки |
| Site Visit | осмотр объекта: запрос, слот, подтверждение, итог |
| Deal | зафиксированная сделка: проект + подрядчик + принятая смета |
| Agreement | документ сделки (scope of work, условия) |
| Change Order | согласованное изменение объёма/цены после фиксации сделки |
| Final Value | итоговая стоимость: принятая смета + одобренные Change Orders |
| Re-match | возврат проекта в Matching после срыва сделки |

# QUOTES

## 5. Жизненный цикл Quote

```text
Draft → Sent → Viewed → Accepted (= DEAL)
         │        │
         │        ├─ update → новая версия → Sent
         │        └─ Declined (клиент отказал / another-selected)
         ├─ Expired  (TTL истёк)
         └─ Withdrawn (мастер отозвал)
```

Переходы необратимы, кроме `update`: обновление создаёт новую версию и возвращает смету в Sent. Состояние Viewed фиксируется в момент первого открытия клиентом (для аналитики и для подрядчика — «смета просмотрена»). При выборе одной сметы остальные активные автоматически переходят в Declined с причиной `another-selected`.

## 6. Структура Quote

Обязательные поля (без них смета не отправляется):

| Поле | Описание |
| --- | --- |
| priceType | fixed / range / hourly (§7) |
| priceLow, priceHigh | вилка в USD; при fixed — одно значение |
| startDate | ориентировочное начало работ |
| durationDays | оценка длительности |
| materialsIncluded | материалы включены в цену: yes/no |
| warrantyMonths | гарантия на работы, месяцев |
| kind | preliminary / final (§8) |
| validUntil | срок действия (§9) |

Необязательные: комментарий (проходит через маскирование контактов, ТЗ №3 §46), вложения (PDF-смета, эскизы — тоже с проверкой на контакты до выбора), а также line items (позиции сметы: работа / материал / кол-во / цена) — line items не в MVP, но схема данных закладывается сразу (§37).

## 7. Типы цены

* **Fixed** — одна сумма; priceLow = priceHigh.
* **Range** — вилка; валидация: priceHigh ≥ priceLow, priceHigh ≤ priceLow × 3 (шире — предупреждение подрядчику «слишком широкая вилка снижает шанс выбора»).
* **Hourly** — ставка $/час + оценка часов; для сравнения система считает эквивалентную вилку (ставка × часы ±20%). Разрешён только для настраиваемого списка категорий (handyman, cleaning, tree service).

## 8. Preliminary vs Final

Смета помечается `kind`:

* **Preliminary** — до осмотра; клиент видит пометку «ориентировочно, до осмотра». Может быть принята напрямую — платформа не заставляет делать осмотр.
* **Final** — после проведённого site visit или когда подрядчик явно пометил смету как финальную. После осмотра система напоминает: «Обновите смету до финальной».

Существенный рост цены final относительно preliminary (> 25%, настройка) помечается для клиента и аналитики (bait-and-switch сигнал, §15).

## 9. Срок действия

`validUntil` — по умолчанию +14 дней (настройка глобально и per-category; подрядчик может указать свой срок в пределах 3–60 дней). За 48 ч до истечения — уведомление обеим сторонам. По истечении — статус Expired; подрядчик может перевыставить смету одним действием («Re-send with new dates»). Истёкшая смета не может быть принята — API возвращает 409 с предложением запросить обновление.

## 10. Подача сметы

Подать quote может только подрядчик со статусом приглашения INTERESTED по этому проекту (ТЗ №3 §34). Форма — mobile-first, предзаполнена умными дефолтами (середина бюджета клиента, ближайший реалистичный startDate по загрузке мастера), целевое время подачи — до 2 минут. Один подрядчик — одна активная смета на проект (новая — только как версия, §11). Клиент получает уведомление **NEW ESTIMATE RECEIVED** (SMS + in-app, ТЗ №2 §61).

## 11. Версионирование

Каждая отправка фиксируется как неизменяемый `QuoteVersion` (§37). При обновлении клиент видит «Смета обновлена» и дельту (было → стало по каждому изменённому полю). Принять можно только последнюю версию; принятие старой — 409 с актуальной версией в ответе (защита от гонки «подрядчик поднял цену в момент принятия»). История версий доступна обеим сторонам и админу; все изменения — в Audit Log.

## 12. Отзыв сметы (Withdraw)

Подрядчик может отозвать смету до её принятия, с причиной (Too Busy / ошибка в цене / Other). Клиент уведомляется. Частые отзывы (> 20% смет за 90 дней) понижают response history в Matching (ТЗ №3 §25) и поднимают флаг админу.

## 13. Экран сравнения (Customer Comparison)

Клиент сравнивает по полям (ТЗ №2 §62): Price / Price Range, Start Date, Duration, Materials, Warranty, Trust Score, Rating, Verified Projects, preliminary/final. Карточный вид на mobile, табличный — на desktop. Первое открытие экрана с ≥ 1 сметой переводит проект в `customer-comparing`.

## 14. Нормализация и бейджи

Для честного сравнения система считает comparable price = середина вилки (hourly — эквивалент §7). Бейджи — только факты: «Лучшая цена» (min comparable price), «Самый ранний старт», «Материалы включены», «Длинная гарантия» (max warranty). Запрещено: «рекомендуем», «лучший выбор» и любое ранжирование, на которое влияет тариф подрядчика (принцип ТЗ №3 §26).

## 15. Аномальные цены

Система флагует (админу, не клиенту):

* цена < 40% или > 250% медианы смет по этому проекту (при ≥ 3 сметах) — возможный демпинг или ошибка;
* систематический bait-and-switch: у подрядчика ≥ 3 случаев роста final над preliminary > 25% за 90 дней;
* цена ниже minJob самого подрядчика (несогласованность профиля).

Пороги — в настройках (§38). Флаг не блокирует смету — решение всегда за админом.

# SITE VISITS

## 16. Site Visit: запрос

Осмотр может запросить любая сторона: клиент — кнопкой Request Site Visit у конкретного мастера; подрядчик — из карточки приглашения («нужен осмотр для точной цены»). Запрос = дата + время (или 2–3 слота на выбор). До выбора подрядчика адрес на осмотр раскрывается **только после подтверждения визита обеими сторонами** и только этому подрядчику: улица + дом, без телефона и email (связь — через чат платформы). Это настраиваемое исключение из privacy-правил ТЗ №2 §95.

## 17. Ответ на запрос

Получатель отвечает: **Accept** / **Suggest New Time** (контр-слот) / **Decline** (с причиной). Статусы Appointment: `requested → confirmed / rescheduled / declined / cancelled → completed / no-show`. Подтверждённый визит переводит проект в статус `site-visit` (если подрядчик ещё не выбран). Переносов не более 3 на визит — дальше только cancel + новый запрос (защита от пинг-понга).

## 18. Напоминания

Обеим сторонам: за 24 ч и за 2 ч до визита (SMS + in-app; каналы и тайминги — настройка). В напоминании подрядчику — адрес и кнопка навигации; клиенту — имя мастера и компания.

## 19. Итог визита и no-show

После слота обе стороны получают вопрос «Осмотр состоялся?»: Yes / No / Rescheduled. Оба «Yes» → `completed`, подрядчику — предложение обновить смету до final (§8). Одностороннее «No» → `no-show` с указанием виновника со слов ответившего; противоречие сторон — флаг админу. No-show подрядчика понижает response history и Trust Score (ТЗ №3 §50); повторные no-show клиента понижают customerResponsive в Lead Score его будущих заявок (ТЗ №2 §43).

## 20. Календарь подрядчика

MVP: список визитов с фильтром по дате + защита от двойного бронирования одного слота (±1 ч). Later: рабочие часы подрядчика, синхронизация с Google Calendar, авто-слоты для клиента по свободному времени.

# ПЕРЕГОВОРЫ

## 21. Чат с контекстом сделки

Переговоры идут в встроенном мессенджере (ТЗ №2 §64). В шапке диалога — контекст: проект, текущая смета и её статус, ближайший визит. События сделки (новая версия сметы, подтверждённый визит, change order) появляются в ленте как системные карточки — история переговоров и история сделки в одном месте.

## 22. Запрос улучшения сметы

Клиент может нажать «Запросить уточнение» на конкретной смете: структурированный запрос (Цена / Сроки / Материалы / Scope / Другое + комментарий), который приходит подрядчику как задача «обновить смету». Это не аукцион: запрос одному мастеру не виден остальным, чужие цены подрядчикам не показываются никогда.

## 23. Counter-offer (later)

Формальный встречный оффер клиента («готов за $X при старте до даты Y») с принятием в один клик — вне MVP; схема данных QuoteVersion его уже поддерживает (`origin: contractor | customer-counter`).

## 24. Маскирование и антиобход в переговорах

До фиксации сделки в чате, комментариях смет и вложениях маскируются телефоны, email, ссылки и соцсети (механизм — ТЗ №3 §46). После фиксации сделки маскирование снимается только в паре «клиент ↔ выбранный подрядчик»; диалоги с остальными остаются маскированными. Счётчик сработавших маскирований на пару участников — входной сигнал детектора обхода (ТЗ №3 §46, п.3).

# DEAL FLOW

## 25. Выбор подрядчика

Кнопка **SELECT CONTRACTOR** на конкретной смете. Подтверждение: «Вы уверены, что хотите выбрать этого подрядчика?» + необязательный вопрос о причинах отказа остальным (Price / Availability / Reviews / Communication / Experience / Other — в аналитику, ТЗ №2 §66). Атомарно в одной транзакции: смета → Accepted; остальные активные → Declined (`another-selected`) с уведомлением мастерам; проект → `contractor-selected`; создаётся Deal (§26).

## 26. Deal — фиксация сделки

Неизменяемое ядро записи: projectId, contractorId, customerId, принятая QuoteVersion, agreedValue (при range — вилка + midpoint для аналитики), startDate, durationDays, createdAt. Изменяемое — только через Change Orders (§30) и статусы (`active → completed / cancelled / disputed`). Deal — единственный источник правды для Total Project Value Created и будущего биллинга (ТЗ №5).

## 27. Раскрытие контактов

В момент создания Deal выбранный подрядчик получает: полный адрес, телефон, email и полное имя клиента; клиент — прямые контакты мастера. Остальные участники матчинга контактов не получают никогда. Факт раскрытия пишется в Audit Log.

## 28. Договорные документы (Agreement)

MVP: платформа генерирует PDF «Scope of Work Summary» из данных сделки (стороны, описание работ, сумма, сроки, гарантия, дисклеймер «платформа не сторона договора»). Документ доступен обеим сторонам в карточке сделки; шаблон редактирует админ (ТЗ №2 §98 Templates). Стороны могут приложить свой подписанный договор (PDF, в приватное хранилище, signed URLs). Later: e-signature, юридические шаблоны по типам работ (требования PA HICPA — отдельная юридическая проработка до запуска фичи).

## 29. Депозит и оплаты

Платежи через платформу — вне модуля (ТЗ №2 §101). Фиксируются только факты со слов сторон: размер депозита (если был), отметка «депозит оплачен». Эти поля готовят данные для будущего платёжного модуля, не создавая обязательств.

## 30. Change Orders

После фиксации сделки любое изменение объёма/цены — только Change Order (ТЗ №2 §69): описание + сумма (±) + влияние на сроки. Создаёт подрядчик (later — и клиент); клиент — Approve / Reject, без ответа 7 дней — напоминание, статус остаётся pending. Вся история — в карточке сделки и Audit Log. Отклонённый CO не меняет ничего; спор по CO → dispute-процесс (§33).

## 31. Final Value

```text
Final Value = agreedValue (midpoint при range)
            + Σ approved Change Orders
```

Считается автоматически, пересчитывается при каждом approved CO, фиксируется при подтверждении завершения клиентом (ТЗ №2 §70). Именно Final Value идёт в Lifetime Project Value клиента, VIP-правила (ТЗ №2 §81) и Total Project Value Created (ТЗ №2 §86).

# СРЫВЫ, СПОРЫ, SLA

## 32. Срыв сделки и re-match

Сделку может отменить любая сторона до начала работ (после начала — только через dispute, §33). Причина обязательна. Последствия:

* **Отменил подрядчик** (contractor cancelled): проект возвращается в статус `qualified` с флагом срочности (stage = contractor-cancelled, ТЗ №2 §26) и автоматически уходит в **re-match** (ТЗ №3); прежние interested-мастера приглашаются первыми, их сметы можно реактивировать одним действием. Отмена без уважительной причины понижает Trust Score.
* **Отменил клиент**: проект → `cancelled` или, по желанию, обратно в сравнение (если другие сметы ещё действительны). Частые отмены после раскрытия контактов — сигнал обхода платформы (ТЗ №3 §46).

## 33. Споры (Disputes)

Любая сторона может открыть спор из карточки сделки: категория (цена / качество / сроки / неявка / CO / другое) + описание + вложения. Проект → `disputed`, админу — задача High priority, SLA первой реакции — 24 ч. Решения админа: вернуть в работу / отменить сделку (с re-match или без) / закрыть с пометкой. На время спора пара «клиент ↔ подрядчик» исключается из новых матчей друг с другом (ТЗ №3 §16 RISK_HOLD). Исход спора влияет на Trust Score.

## 34. SLA этапа

| Метрика | Цель | Алерт админу |
| --- | --- | --- |
| Interested → первая смета (без визита) | ≤ 24 ч | > 48 ч (ТЗ №2 §92) |
| После визита → final quote | ≤ 48 ч | > 72 ч |
| Ответ на запрос визита | ≤ 12 ч | > 24 ч |
| Клиент сравнивает без выбора | — | > 7 дней → follow-up клиенту, > 14 → админу |
| Реакция на dispute | ≤ 24 ч | > 24 ч |

Все пороги — в настройках (§38). Follow-up клиенту при долгом сравнении: «У вас N предложений. Нужна помощь с выбором?» + вариант «ни одно не подошло» с причинами (в аналитику и в re-match).

## 35. Уведомления этапа

Клиенту: NEW ESTIMATE RECEIVED · смета обновлена / отозвана / истекает · визит подтверждён / перенесён · напоминания о визите · Change Order · follow-up сравнения.
Подрядчику: смета просмотрена · запрос уточнения · запрос/ответ по визиту · ВЫ ВЫБРАНЫ (с контактами) · смета отклонена (another-selected, без чужих цен) · CO approved/rejected · сделка отменена.
Админу: аномальная цена · противоречие по визиту · SLA-нарушения · dispute · подозрение на обход.
Каналы и шаблоны — через общий Notifications-сервис (ТЗ №2 §89, §98); событийные имена — в §36.

# API И ДАННЫЕ

## 36. API и события

```text
POST   /api/v1/projects/{id}/quotes            — подать смету (только interested)
PUT    /api/v1/quotes/{id}                     — новая версия
POST   /api/v1/quotes/{id}/withdraw            — отозвать (причина обязательна)
POST   /api/v1/quotes/{id}/accept              — принять (только customer; создаёт Deal)
POST   /api/v1/projects/{id}/appointments      — запрос визита
POST   /api/v1/appointments/{id}/respond       — accept / reschedule / decline
POST   /api/v1/appointments/{id}/outcome       — completed / no-show
POST   /api/v1/deals/{id}/change-orders        — создать CO
POST   /api/v1/change-orders/{id}/decide       — approve / reject
POST   /api/v1/deals/{id}/cancel               — отмена (причина обязательна)
POST   /api/v1/deals/{id}/disputes             — открыть спор
```

Правила: все мутации идемпотентны (Idempotency-Key); accept проверяет актуальность версии и validUntil (иначе 409); доступ строго по ролям (подрядчик видит только свои сметы, чужие цены не отдаются ни одним endpoint'ом).

События: `quote.sent | viewed | updated | withdrawn | expired | accepted | declined` · `visit.requested | confirmed | rescheduled | declined | completed | no-show` · `deal.created | cancelled | disputed | value-changed` · `change-order.created | approved | rejected`. Потребители: Notifications, CRM, Analytics, Matching (re-match, response history), будущий Billing.

## 37. Сущности (дополнение к ТЗ №2 §97)

## 38. Админ-настройки (без разработчика)

quote validity по умолчанию и пределы · допустимая ширина вилки · список hourly-категорий · пороги аномалий (§15) и bait-and-switch (§8) · лимит переносов визита · тайминги напоминаний · все SLA §34 · шаблон Agreement · правило раскрытия адреса на визит (§16: вкл/выкл) · тексты уведомлений. Каждое изменение версионируется.

## 39. Инструменты админа

Карточка проекта дополняется: все сметы с версиями и флагами аномалий, визиты, сделка с CO-историей, споры. Действия: скрыть смету (нарушение) · продлить validUntil · отменить сделку с re-match · решить спор · связаться со сторонами. Админ не может редактировать цену сметы — только подрядчик новой версией.

## 40. Аналитика этапа

Quote rate (interested → смета) · среднее смет на проект · time-to-first-quote · visit rate и конверсия визит → final quote → hire · quote → hire по категориям и подрядчикам · win rate по позиции цены (дешевле/дороже медианы) · цена vs бюджет клиента (калибровка budget ranges ТЗ №2 §29) · доля сделок с CO и средний рост Final Value · причины отказов §25 · cancellation rate по сторонам. Эти метрики питают learning loop ТЗ №3 §49 (MatchOutcome).

## 41. Security / privacy

RBAC на каждый endpoint; цены подрядчиков — коммерческая тайна (не отдаются другим мастерам ни в API, ни в уведомлениях); вложения — приватное хранилище + signed URLs; раскрытие PII — только по правилам §16/§27 с записью в аудит; rate limiting на подачу/обновление смет.

# КАЧЕСТВО И ПРИЁМКА

## 42. Тестирование

1. **Unit:** переходы жизненного цикла (все недопустимые — отказ), валидация вилки, validUntil и auto-expire, расчёт Final Value с CO (±), лимит переносов, детект аномалий по граничным значениям.
2. **Гонки:** accept старой версии при одновременном update; два accept разных смет одного проекта параллельно — ровно один Deal; withdraw vs accept.
3. **E2E:** interested → визит → final quote → сравнение → выбор → раскрытие контактов → CO → завершение; срыв сделки подрядчиком → re-match.
4. **Privacy-тесты:** ни один endpoint/уведомление не отдаёт чужие цены или PII до положенного момента (автотест на сериализаторы).

## 43. Acceptance Criteria

Модуль готов, когда:

* interested-подрядчик подаёт структурированную смету с телефона за ≤ 2 минуты;
* клиент получает NEW ESTIMATE RECEIVED и видит сравнение по всем полям §13;
* обновление сметы создаёт версию с видимой дельтой; принять можно только последнюю;
* визит проходит полный цикл requested → confirmed → completed с напоминаниями;
* SELECT CONTRACTOR атомарно создаёт Deal, отклоняет остальные сметы и раскрывает контакты только выбранному;
* CO проходит цикл pending → approved/rejected и меняет Final Value;
* отмена подрядчиком автоматически возвращает проект в re-match;
* все события §36 публикуются, все действия — в Audit Log;
* настройки §38 меняются админом без релиза;
* privacy-тесты §42.4 зелёные.

## 44. MVP-объём

**В MVP:** quote с обязательными полями §6 (fixed/range), версии, withdraw, validity/auto-expire; экран сравнения с факт-бейджами; site visits с напоминаниями и итогом; запрос уточнения §22; выбор + Deal + раскрытие контактов; generated Agreement PDF; Change Orders; Final Value; отмена + re-match; споры базово; аналитика §40 базово.

**Не в MVP:** line items; hourly-цены; counter-offer; e-signature; календарные интеграции; авто-слоты визитов; платежи/депозиты (кроме отметок §29); ML-детект аномалий.

## 45. Следующий модуль

**ТЗ №5 — Монетизация и биллинг:** модели оплаты лидов (pay-per-lead / подписка / комиссия с Deal), тарифы подрядчиков, биллинг LeadAllocation (ТЗ №3 §42) и Deal/Final Value из этого ТЗ, возвраты за плохие лиды, отчётность. Именно здесь платформа начинает зарабатывать — на данных, которые модули №1–№4 уже фиксируют.
